The message

A recruiter found me on LinkedIn for a Lead DevOps/SRE role. The stack: EKS, Fargate, Aurora, Terraform/Terragrunt, Argo CD, GitHub Actions, Datadog. The ask underneath the tool list: can you build and run a reliability practice, not just click deploy.

I'd built pieces of this before, separately. I hadn't built the whole story in one place — something that actually breaks, and a real number for how fast I got it back. So instead of just replying with a resume, I decided to build the story first.

ACT 02 — THE BUILD~300 words

Standing it up

I started with the network, then the cluster, then the delivery pipeline — the same order a real platform team would, not the order that looks best in a demo.

Screenshot 2 of 13

`terragrunt run-all plan` output, full resource list, before anything exists. Caption idea: "before I touch AWS, here's the exact list of what's about to get created — no surprises."

One decision worth explaining up front: I ran this as a Fargate-only cluster — no EC2 node group at all. AWS runs every pod in its own micro-VM; I don't patch or size servers. The real tradeoff — no DaemonSets, so the observability agent later needs a different install path — is documented in ADR 001 rather than glossed over.

Screenshot 3 of 13

AWS Console → VPC → Resource Map. Two AZs, public/private split, one NAT per AZ.

The first real snag showed up exactly where I expected it to, twice — once on the first deploy, then identically again on a later redeploy, which is what confirmed it wasn't a fluke: CoreDNS came up stuck Pending, zero scheduling events, until I deleted the pods so they'd be recreated after their Fargate profile had actually finished applying. EKS auto-deploys CoreDNS the instant the control plane is up — before Terraform necessarily finishes the matching profile a few seconds later. A Fargate-only cluster has no fallback node to catch anything born too early.

ACT 03 — THE DRILLdone — MET, 39.032s

Breaking it on purpose

Anyone can deploy a database. The part worth writing about is what happens when it goes away mid-traffic — because that's the actual job.

Target RTO going in: 2 minutes — set before the drill, in the runbook, based on AWS's own documented typical Aurora failover times.

I stood up continuous traffic against the app's /readyz endpoint — the one that actually touches Aurora, not just a liveness check — polling every ~2.3 seconds through a tunnel, logging every request's timestamp and status. Then, with steady 200s confirmed, I issued a real aws rds failover-db-cluster. Not a reboot. Not a simulation. A genuine forced promotion of the standby instance, verified afterward by checking that the writer and reader roles in AWS had actually swapped.

Screenshot 8 of 13 — the failure

Terminal output of aws rds failover-db-cluster, timestamped 19:53:38.819 UTC — this is T+0 for everything that follows.

For about 10.5 seconds, nothing happened — the app kept serving fine while Aurora's internal cutover was still in progress. Then 5 requests in a row came back 503, each one a clean, honest {"detail":"database unreachable"} from the app itself — not a hang, not a generic error. Real downtime: about 16 seconds. Then it started working again, and stayed working.

Screenshot 11 of 13 — recovery

aws rds describe-db-clusters output showing the writer/reader roles swapped — the AWS-side proof, separate from the app's own signal. Recovered in 39.032 seconds against a 2-minute target RTO — MET, with real margin, not a photo finish.

The honest reading isn't just the headline number. There's a real gap between when the service actually came back (first successful request, ~29 seconds in) and when I'd call it confirmed-stable (5 successes in a row, ~39 seconds in) — that 10-second buffer against a single lucky response mid-flap is part of the measurement discipline, not padding. If the number had missed the target, it goes in anyway, with whatever caused it. It didn't this time, and it's still reported as measured, not as a foregone conclusion.
